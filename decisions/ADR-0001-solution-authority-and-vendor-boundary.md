# ADR-0001：方案权威层级与 Vendor 边界

- 状态：accepted
- 日期：2026-07-21
- 决策人：项目负责人（本次工作流确认）
- 相关 Source ID：SRC-0001～SRC-0019
- 相关 Requirement ID：无
- 替代关系：首次建立

## 背景

项目同时存在系统级安全方案、软件落地方案、Vendor eHSM 文档/代码和 Vendor 建议。若不明确层级，容易把 eHSM 局部实现误写成 SoC 架构事实，或把尚未纳入内部方案的 Vendor 建议直接当作项目设计。

## 候选方案

1. 所有资料平级，由具体任务临时选择。
2. Vendor 文档和代码直接作为 SoC 设计依据。
3. 建立“系统安全方案 → 安全软件方案 → 工程实现”的内部权威链，Vendor 资料只作为 eHSM 输入。

## 决策

采用方案 3，并形成以下项目硬约束：

1. `SRC-0017 芯片系统安全方案`是系统级、架构级上位方案，粒度较粗，定义硬件基础、系统架构和安全原则。
2. `SRC-0016 芯片安全软件方案`是基于 SRC-0017 的下位软件方案，以工程落地为目标；其硬件前提、架构边界和原则必须依赖并符合 SRC-0017。
3. 本项目所称 Vendor 仅指 eHSM 及 eHSM 内部 Core，不包含 NGU800P SoC。Vendor 文档、代码和建议不得直接定义 SoC 行为或 SoC 方案。
4. Vendor 建议只有被项目采纳并写入“芯片安全软件方案”后，才成为项目软件方案的一部分。软件实现和软件侧最终方案以最新有效的“芯片安全软件方案”为准。
5. 密钥轮换策略已批准；具体流程、参数、接口和工程实现仍必须体现在“芯片安全软件方案”中。Vendor 定制建议本身不作为最终方案基线。
6. 对本工程而言，Vendor 文档不按保密资料管理；若源文件带有 Vendor confidentiality 标记，保留该标记的客观记录，但项目分类为 `NOT_CONFIDENTIAL_FOR_THIS_PROJECT`。
7. Vendor 代码按交付快照整体登记，不逐文件建立 Source Card。后续代码更新应附具体 delivery/release note，并登记为新的 Source ID，通过 `Supersedes` 关系连接旧快照。

## 选择理由

- 保持 SoC 架构决策由内部系统方案控制。
- 允许 Vendor 实现和建议被充分利用，同时避免 eHSM 局部结论越权外推。
- 让软件方案成为采纳决策与工程落地之间的受控接口。
- 以交付快照管理大规模 Vendor 代码，兼顾可追踪性和维护成本。

## 安全影响

- 密钥轮换策略的批准状态已明确，但在软件方案未记录完整细节前，不得臆测轮换周期、Key Slot、OTP bitmap、回退或生命周期行为。
- Vendor eHSM/Core 结论不得直接标为 SoC `CONFIRMED` 行为。
- 系统方案与软件方案不一致时，先按上位系统原则识别冲突，再通过方案评审/OpenSpec 收敛软件实现。

## 软件影响

- 新增或修改安全软件行为时，必须说明其 SRC-0017 上位依据以及是否已经进入 SRC-0016 或其后续版本。
- 采纳 Vendor 建议但尚未写入软件方案时，状态保持 `PROPOSED`，不得直接安排正式实现。
- Vendor 新代码版本按交付 note 建立新快照记录，不逐文件登记。

## 测试影响

- 测试预期优先来自内部方案和已批准需求；Vendor tests 只能证明对应 eHSM 快照下的实现表现。
- 密钥轮换测试矩阵应在软件方案明确流程和接口后建立，并覆盖异常、回退、掉电和生命周期边界。

## 风险

- 当前 SRC-0016/SRC-0017 的正式版本号、Owner 和完整审批记录仍需补齐。
- 已批准密钥轮换策略是否已经完整体现在 SRC-0016 v1.2 中，需要后续章节级核对。
- Vendor 文档的项目“不保密”分类不改变第三方版权、授权范围或对外传播规则；若公司另有分发制度，仍应遵守。
