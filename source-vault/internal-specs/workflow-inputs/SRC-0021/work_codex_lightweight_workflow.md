# Work × Codex 轻量协作工作流

## 1. 目标

本工作流用于解决以下问题：

- 方案梳理、收敛和详细设计由 **Work** 主导；
- 代码仓库位于远端环境，代码调查与实现由 **Codex** 主导；
- 保留人工确认点，避免代码事实、设计推断和架构决策混在一起；
- 通过固定目录、标准任务单和证据报告，减少在 Work 与 Codex 之间反复复制上下文；
- 使总体方案、详细设计和实际代码保持可追踪、可核验、可更新。

本流程当前采用**人工分工、文档交接**，暂不采用 Work 自动调用远端 Codex CLI。

---

## 2. 角色分工

### 2.1 Work：方案负责人

Work 负责：

1. 梳理需求、规范、硬件约束和项目背景；
2. 组织方案讨论并推动架构收敛；
3. 编写总体方案和详细设计；
4. 识别设计中需要通过代码确认的问题；
5. 创建结构化的代码调查任务；
6. 阅读 Codex 输出的代码证据报告；
7. 对关键结论抽查源代码；
8. 区分代码现状、目标设计和待确认事项；
9. 更新正式设计文档和差异追踪表；
10. 保证文档前后一致、术语统一、结论有依据。

Work 不应仅根据已有方案文档推断代码现状，也不应将现有代码直接等同于目标设计。

### 2.2 Codex：代码事实负责人

Codex 负责：

1. 在远端真实代码仓库中搜索和阅读代码；
2. 跟踪跨文件、跨目录调用链；
3. 检查宏、Kconfig、Makefile、链接脚本和构建配置；
4. 确认接口、结构体、寄存器、错误码和状态机的真实实现；
5. 必要时查看 Git 历史和变更记录；
6. 执行编译、测试和静态检查；
7. 输出带文件路径、符号和判断依据的代码证据报告；
8. 在进入实现阶段后，根据详细设计修改代码并验证。

在“代码调查”阶段，Codex 默认只读，不修改业务代码。

### 2.3 人工确认点

以下内容必须由人工参与判断：

- 安全架构是否合理；
- 现有代码是否应当保留；
- 代码事实对目标方案意味着什么；
- 硬件、软件、进度和风险之间如何取舍；
- 证书链、密钥轮换、生命周期和安全边界等架构决策；
- 代码与文档冲突时，以哪一方为准；
- 哪些内容已经收敛，哪些仍需评审。

## 4. 核心流程

```text
Work 梳理方案
    ↓
识别需要代码确认的问题
    ↓
Work 创建调查任务单
    ↓
人工将任务交给远端 Codex
    ↓
Codex 调查真实代码并输出证据报告
    ↓
Work 阅读报告并抽查关键源码
    ↓

    ↓
Work 更新总体方案或详细设计
    ↓
Codex 按详细设计实现和验证
    ↓
Work 更新设计追踪和变更记录
```

## 5. 阶段一：Work 梳理方案

Work 在方案讨论和文档编写过程中，应主动识别以下问题：

- 当前结论是否依赖代码现状；
- 是否存在未确认的调用链；
- 是否涉及条件编译或平台差异；
- 是否需要确认接口是否已经实现；
- 是否需要确认错误路径和异常边界；
- 是否需要确认现有构建和链接方式；
- 是否存在“文档这么写，但代码可能不是这样”的风险。

发现上述问题时，不应直接猜测，应创建代码调查任务。

### Work 的输出要求

正式设计文档中的内容应尽量标注为以下类别：

- **代码现状**：已经通过代码证据确认；
- **目标设计**：项目计划采用的最终方案；
- **差异项**：现有实现与目标设计不一致；
- **待确认项**：暂时没有足够证据；
- **决策项**：需要人工或评审会议决定。

---

## 6. 阶段二：创建代码调查任务

每个调查任务应尽量小而聚焦，不要一次要求 Codex“分析整个安全方案”。

### 推荐任务粒度

好的任务：

- 确认 BootROM 等待 eHSM ready 的实现；
- 确认 FMC 镜像验签、解密、加载和跳转调用链；
- 确认密钥槽 bitmap 的读取和使用位置；
- 确认 USER 生命周期下 OTP 写入权限控制；
- 确认 Debug 鉴权后的 gating 控制路径；
- 确认 measurement 数据由哪些模块生成。

不推荐的任务：

- 分析整个安全启动代码；
- 检查全部安全方案；
- 找出所有问题；
- 理解整个项目架构。

### 任务编号规则

建议使用：

```text
NNN-主题简写.md
```

例如：

```text
001-bootrom-ehsm.md
002-key-slot-selection.md
003-debug-auth-gating.md
004-spdm-measurement.md
```

## 7. 调查任务模板

文件：`docs/templates/investigation-task-template.md`

```markdown
# 调查任务：<任务名称>

## 1. 背景

说明该任务来自哪个设计问题、方案章节或评审意见。

## 2. 调查目标

用一句话说明本次调查需要确认的核心事实。

## 3. 需要回答的问题

1. 问题一；
2. 问题二；
3. 问题三；
4. 问题四。

## 4. 建议检查范围

- 目录：
- 文件：
- 模块：
- 关键字：
- 可能相关的函数、结构体、寄存器或宏：

注意：建议范围仅用于提高搜索效率，不应限制 Codex 查找必要的关联代码。

## 5. 证据要求

每个结论必须尽量提供：

- 文件路径；
- 函数、结构体、宏、寄存器或符号名称；
- 关键代码位置或行范围；
- 调用关系；
- 判断依据；
- 是否受条件编译影响；
- 是否存在多平台或多版本差异。

## 6. 输出要求

请输出到：

`docs/code-evidence/<对应报告名称>.md`

报告必须区分：

- 已确认事实；
- 合理推断；
- 无法确认；
- 与现有设计不一致；
- 建议进一步调查。

## 7. 限制

- 当前阶段只调查，不修改业务代码；
- 不根据函数名、注释或文件名直接猜测实现；
- 必须阅读关键函数体；
- 不把目标设计当成代码现状；
- 不把代码现状直接当成最终设计；
- 不确定时明确写出“不确定”及原因。
```

## 14. 实现阶段流程

详细设计收敛后，由 Codex进入实现阶段。

```text
Work 输出详细设计
    ↓
人工确认设计基线
    ↓
Codex 根据详细设计修改代码
    ↓
Codex 编译、测试和静态检查
    ↓
Codex 输出实现报告
    ↓
Work 对照设计检查偏差
    ↓
更新设计、代码追踪和变更记录
```

进入实现阶段后，Codex 的任务应明确：

- 可修改的目录和文件；
- 禁止修改的模块；
- 接口兼容要求；
- 需要执行的编译和测试；
- 预期输出；
- 回滚要求；
- 是否允许调整设计。

如果实现中发现设计不可落地，Codex 应停止扩大修改，并输出设计冲突，不应自行改变安全架构。

## 15. 关键原则

### 15.1 代码事实不等于目标设计

现有代码只能说明“当前实现是什么”，不能直接证明“最终方案就应该这样”。

### 15.2 目标设计不等于代码现状

正式设计中的内容如果尚未实现，应明确标注“待实现”，不能描述为已有能力。

### 15.3 所有关键结论尽量有证据

关键结论至少应关联以下一种证据：

- 代码文件和符号；
- 硬件 TRM；
- 标准规范；
- 评审纪要；
- 设计决策记录；
- 测试结果。

### 15.4 调查任务应小而明确

每个任务尽量只解决一个核心问题，避免 Codex 扫描大量无关代码。

### 15.5 保留人工审查点

Work 与 Codex 之间不自动闭环。涉及架构、安全和风险取舍时，必须由人工确认。

### 15.6 不确定时明确标注

禁止用模糊语言把推断包装成事实。无法确认时，应说明缺少什么信息。

```text
9. 完成后向我说明：
   - 创建了哪些文件；
   - 哪些调查任务优先级最高；
   - 当前方案中最需要代码确认的风险点；
   - 下一步建议我先把哪个任务交给远端 Codex。
```

## 18. 当前推荐使用方式

日常工作按以下方式执行：

```text
Work：方案讨论、任务拆分、设计更新
Codex：远端代码调查、实现和验证
人工：任务交接、架构决策和关键结论审查
文档：任务、证据、设计和变更的统一载体
```

在流程稳定、任务模板成熟、重复性调查明显增多后，再考虑将部分只读、格式固定的任务封装为远端 `codex exec` 自动化脚本。
