## 2. 最终表格格式

1. 类别名称；
2. 模块名称；
3. 测试用例描述；
4. 用例编号；
5. 用例类型；
6. 优先级；
7. 前置条件；
8. 输入；
9. 输出；
10. 测试目的；
11. 通过准则；
12. 归属团队；
13. 负责人。

表头使用黄绿色底色；类别、用例类型、优先级和团队使用有语义的浅色底色及下拉项；正文自动换行、冻结表头，允许直接复制或导入飞书表格。

## 3. 用例内容粒度

### 3.1 前置条件

必须写明电源/时钟/复位/阶段、资源独占、前序用例、参与核或Master、IRQ/Debug/EDA环境，以及一次性资源和恢复条件。仅写“环境就绪”不满足要求。

### 3.2 输入

输入栏按可执行步骤写清：

- 操作对象和范围；
- 具体测试值、向量或生成规则；
- 执行顺序和循环维度；
- 超时/等待条件；
- 实际中断、Mailbox或MMIO通路；
- 读回、清理和恢复动作。

不使用未解释的`pattern`、`peer`、`sequence`等词替代具体设计。

### 3.3 输出

只写测试软件或EDA实际采集的数据，例如原始寄存器、Mailbox响应、返回码、输出缓冲区、IRQ来源/计数、对象/Flash/OTP/状态前后快照、波形和恢复结果；不把期望结果重复写成输出。

### 3.4 测试目的和通过准则

- 测试目的说明本用例证明哪一项功能或安全属性。
- 通过准则必须能直接判定PASS/FAIL，包含数量、值、状态变化、无副作用、清理和恢复要求。
- 未冻结的地址、位定义、错误码或清除语义不得猜测PASS，应返回`INCONCLUSIVE`并记录解除条件。

## 4. 用例组织原则

1. 数量有限且可自动遍历的同构实例，在同一用例内全覆盖。
2. 端点、实例和输入值等已经分别证明且相互正交的维度，不展开无收益的全笛卡尔积。
3. 多核/Master、中断、Debug和EDA场景必须验证真实路径，不能用单核顺序访问、软件伪中断或寄存器自写替代。
4. 有副作用的读取、不可逆资源和复位/中断操作，必须在步骤中明确清理、恢复和超时。
5. 先形成架构/功能说明，再冻结用例表，最后生成13列CSV/XLSX；最终表和说明文档互相引用。
