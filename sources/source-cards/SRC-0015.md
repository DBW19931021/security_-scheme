## Key security content

定制需求方案包含 SoC Key 轮换和 OTP Key 映射复用：

- 第1页：轮换对象为 SoC Verify、Encrypt、Debug Key；每类只允许一次轮换；新增1字节、由HSM内部管理的OTP Bitmap。
- 第2～4页：外部管理系统生成48字节双层密文；USER下先做SoC Challenge-Response；eHSM按“解密/校验→写新Key→更新Bitmap→destroy旧Key”执行；成功后SoC硬件复位eHSM并由上电流程加载新Key。
- 第3页：48字节结构为`key attributes[4] + ciphertext_A[32] + CRC32[4] + key_type[4] + padding[4]`，外层再由`RTL SoC KEK`保护。
- 第4页：机制依赖外部系统托管`RTL SoC KEK`、`CHIP_ROOT_KEY`和`DEVICE_ROOT_KEY`相关能力；具体生成和托管模型需由项目KMS/制造方案冻结。
- 第5页：slot 9～14和Verify `bit0`均是示例；实际OTP排布和Key映射由客户决定。启动/升级复用SoC Verify/Encrypt Key，eHSM启动/升级也复用各自Verify/Encrypt Key。

项目已批准密钥轮换策略，并于2026-07-27通过ADR-0021确认轮换机制参考本来源；具体物理绑定、Vendor定制ABI、KMS recipe和掉电恢复仍以芯片安全软件详细设计及后续有效软件方案为准。

2026-07-29负责人进一步确认：量产RTL Key按die唯一，KMS按设备托管`RTL SoC KEK`及Root Key相关句柄并生成设备专属双层密文。因此SRC-0015轮换流程与一机一密不存在概念冲突；当前问题只是匹配Vendor定制交付尚未到齐。

## Known limitations

- PDF明确声明所有slot编号和Key映射为示例，不可直接生成NGU800P OTP配置。
- 未给出专用Mailbox command ID/结构体/状态码、Bitmap真实bit映射、写入原子粒度、掉电查询、幂等性和寿命/耗尽语义。
- 未给出两层加密的算法/mode/IV、字段字节序、Key属性编码、CRC参数、padding值，以及命令外层`key_type`与密文内副本如何校验。
- Vendor流程在首次以新Key启动验证前destroy旧Key；Bitmap提交和destroy窗口的掉电恢复仍需Vendor证明和项目裁决。
- 当前SRC-0018交付只有通用安装命令，且FW拒绝USER/DEBUG生命周期安装；没有本PDF要求的专用轮换命令和Active Bitmap逻辑，见CE-SEC-013。
- 本PDF整体仍是`PROPOSED` Vendor定制方案；只有ADR-0021明确吸收的轮换机制成为受控软件方案增量。
